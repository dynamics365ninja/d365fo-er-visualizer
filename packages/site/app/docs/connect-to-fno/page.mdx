Exporting configurations by hand gets old quickly. The live connection signs you in to a Finance
&amp; Operations environment and downloads ER configurations straight from it — read-only, using
your own permissions.

## What you need

- The **environment URL**, for example `https://myenv.sandbox.operations.dynamics.com`.
- A user account with access to Electronic Reporting in that environment.

That is it. The app ships with its own multi-tenant Entra application registration, so a
connection profile is just a name and a URL — there is no client ID or tenant ID to look up, and
you do not create an app registration. Clicking **Connect** opens the ordinary Microsoft sign-in:
you pick your work account, approve the consent prompt the first time, and you are in. If your
tenant blocks user consent, an administrator approves it once for everyone.

## Create a connection profile

In the app, switch to the **D365 F&amp;O server** tab and click **New profile**. Fill in:

| Field | Value |
|---|---|
| **Profile name** | Anything you will recognise — `Contoso UAT` |
| **Environment URL** | `https://myenv.sandbox.operations.dynamics.com` |

The URL is the address F&amp;O runs on, with no path after the domain. Click **Save profile**, then
**Connect**. Microsoft sign-in opens in a popup — or, when the browser will not let a popup
through, the whole tab goes to Microsoft and comes back — and the panel then shows **Connected as**
with your account. Profiles are stored in your browser's local storage so you only do this once
per environment; **Edit profile** changes one, and **Remove profile** deletes it together with its
saved sign-in after asking you to confirm.

Everything the tool then does runs as *you*: your Electronic Reporting permissions in that
environment decide what you can see, and nothing is written back.

## Self-hosting: register the application

Skip this unless you are building and hosting the tool yourself — users of a ready-made build
never touch it.

A build signs in with the shipped registration, whose client ID is baked into
`packages/ui/src/fno/built-in-client.ts` (`packages/electron/src/fno/built-in-client.ts` for the
desktop shell). `VITE_FNO_CLIENT_ID` (`FNO_CLIENT_ID` for the desktop shell) overrides it. A copy
you host on your own origin needs its own registration, because the redirect URI has to be listed
on it; with the variable set to an empty value the connect panel refuses to sign in and says so.
Create the registration once, in any tenant you control:

In the Entra admin center, go to **App registrations → New registration**.

1. Give it a name — `ER Visualizer` is fine.
2. Under **Supported account types**, pick **Accounts in any organizational directory
   (multitenant)**. This is what lets your users sign in from their own tenants.
3. Add the platform you will use, under **Authentication → Add a platform**:
   - **Single-page application** — redirect URI is the origin the app is served from, for example
     `https://your-er-visualizer-domain` (no path). For local development that is
     `http://localhost:5173`. Entra matches this string verbatim, so leave off the trailing slash,
     and note that every Vercel preview deployment has its own hostname and needs its own entry.
     A misconfigured build prints the exact value to paste.
   - **Mobile and desktop applications** — add `http://localhost` if you ship the
     [desktop app](/docs/desktop-app). The loopback flow picks a free port at runtime, and Entra
     matches any port for `http://localhost`.
4. Under **Authentication → Advanced settings**, set **Allow public client flows** to **Yes**.
   This is what the desktop loopback flow needs.
5. Under **API permissions → Add a permission → Dynamics ERP**, add the single **delegated**
   permission `CustomService.FullAccess`. The ER services this app calls live under
   `/api/services`; no OData entity is ever read, so no OData permission is needed.
6. The permission is user-consentable, but Microsoft's default tenant policy
   (`ManagePermissionGrantsForSelf.microsoft-user-default-low`) only lets users self-consent to
   permissions *classified as low impact*, and Dynamics ERP scopes are not classified by default.
   Most tenants therefore need a one-time administrator approval — see
   [Troubleshooting](/docs/troubleshooting).

Copy the **Application (client) ID** from the registration overview into `VITE_FNO_CLIENT_ID`.
There is no tenant ID to configure: sign-in uses the shared `organizations` authority, and the
tenant comes back on the token from whichever account the user picks.

> The application is a public client — there is no client secret anywhere in this setup, and none
> is needed. Sign-in happens with authorization code plus PKCE, and the resulting token lives in
> the browser session only.

### Register the user in Finance &amp; Operations

A **service-to-service** registration also has to be known to the environment: in F&amp;O, open
**System administration → Setup → Microsoft Entra ID applications** and add a row with the client
ID, a name, and the user account whose permissions the calls should run under. This step does not
apply to the sign-in flow used here — the token already carries your own identity, so your regular
F&amp;O user permissions are what count.

## Browse and ingest

Once connected, the panel walks the ER hierarchy of the environment in two columns:

1. **ER solutions** (left) — the data models of the environment. Pick one to see the
   configurations built on it; **Filter models…** narrows the list, and **Search formats too**
   also looks through the formats and mappings underneath every model (it downloads each model's
   configuration list, so a large environment takes a while).
2. **Configurations** (right) — tick the ones you want. You can filter by component type or by
   name, drill into a configuration's children, use **Select all** or **Clear selection**, and keep
   selections across drill levels — the footer shows how many are selected in total. When you tick
   a format, the panel offers its data model and model mapping from the same list (**Also load
   related configurations?**).
3. **Load selected** — downloads and parses everything you picked. **Cancel download** stops a
   download that is running.

The download shows its progress in a dialog, **Downloading configurations from F&amp;O**: a stepper
through **Preparing**, **Data models**, **Formats &amp; mappings**, **Model mappings** and
**Finalizing**, a status line naming the exact step, and one row per configuration marked
**selected** or **dependency** with its state — **Done**, **No own XML**, **Skipped** or
**Failed**. Dependencies are why a load sometimes pulls in more configurations than you selected:
data models and mappings referenced from the downloaded XML are fetched so bindings actually
resolve. When something did not arrive, the dialog stays open after the download so you can see
what and why.

Configurations loaded this way behave exactly like files opened from disk, and cross-reference
them freely.

## Notes and limits

- **Derived configurations are skipped.** A configuration that inherits from another one has no
  XML of its own; load the base configuration instead. The tool tells you which ones it skipped.
- **Draft-only configurations cannot be downloaded.** F&amp;O serves completed versions only, so a
  configuration with nothing but a draft is marked **Draft** and cannot be ticked. Complete the
  version in F&amp;O (**Reporting configurations → Versions → Complete**) and it becomes
  selectable.
- **Model mappings are not always downloadable.** When `GetModelMappingByID` returns nothing for a
  data model, the panel says so — format element bindings still resolve through the format's own
  mapping information, but the mapping-level trace stops there.
- **Import-only formats have no data model to fetch.** For formats that only read files — bank
  statements, for example — the F&amp;O API exposes no data model, so only the format
  configuration itself can be downloaded.
- **An empty solution list is not a sign-in failure.** It means the environment has no ER
  configurations imported yet — see [Troubleshooting](/docs/troubleshooting).
- **Nothing is written back.** Every call the tool makes is a read.

## How the network path works

Finance &amp; Operations does not send CORS headers, so a browser cannot call its services
directly. The hosted app routes those calls through a stateless proxy that forwards the request
server-side, carrying your bearer token, and returns the response with CORS headers attached.

The proxy only forwards to Finance &amp; Operations environment hosts (`*.operations.dynamics.com`
and its regional and sandbox forms, `*.cloudax.dynamics.com`, `*.axcloud.dynamics.com`,
`*.sandbox.ax.dynamics.com`) over HTTPS on the default port, and only for calls coming from the app
itself — it cannot be used as an open relay — and it stores nothing: no tokens, no configuration
content, no logs of your data. The [desktop app](/docs/desktop-app) skips the proxy entirely and
calls the environment directly.

If sign-in or downloading fails, [Troubleshooting](/docs/troubleshooting) lists the errors this
setup actually produces and what each one means.
