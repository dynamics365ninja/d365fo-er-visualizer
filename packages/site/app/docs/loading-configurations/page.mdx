## What you can load

The parser accepts the file shapes that Electronic Reporting exports produce, and works out which
one it is given without being told:

- **Standard exports** — the `ERSolutionVersion` XML that **Exchange → Export as XML file** in the
  Electronic reporting workspace produces.
- **Bare configuration XML** — a file whose root is the version content itself
  (`ERFormatVersion`, `ERModelMappingVersion`, `ERDataModelVersion`, …), without the solution
  envelope. The envelope is filled in before parsing.
- **`ErFnoBundle` payloads** — the wrapper the [live connection](/docs/connect-to-fno) keeps
  configurations in when it downloads them from Finance &amp; Operations' ER services.

Three component types are recognised: **data model**, **model mapping**, and **format**. The type
is detected from the content, not from the file name — renaming a file changes nothing. A model
mapping export that also carries its data model yields both configurations; the model shows up in
the recent lists as *Part of* the file it came from.

The workspace holds one version of each configuration. Loading a newer version replaces the one
that is open; loading an older one than is already open is refused with a message saying which
version is loaded.

## How to load

There are three routes, and they can be mixed freely in one session:

1. **Drag and drop** — drop one or more `.xml` files onto the landing page, or onto the Explorer
   once a workspace is open.
2. **File picker** — click the drop zone, use **Load XML** in the toolbar, or **Add files…** in the
   workspace manager.
3. **Live environment** — the **D365 F&amp;O server** tab downloads configurations directly. See
   [Connect to a live F&amp;O environment](/docs/connect-to-fno).

Everything you load lands in the same workspace. Configurations pulled from an environment sit
next to files opened from disk and cross-reference each other exactly the same way.

## Why you should load all three types

Each component answers a different question, and a trace only reaches the end when all three are
present.

| Component | Answers | Without it |
|---|---|---|
| **Data model** | What data does this solution describe? | Model paths have no structure or types behind them |
| **Model mapping** | Where does that data come from? | Bindings stop at the model path; you never reach the table |
| **Format** | What does the output file look like? | You see sources but not what consumes them |

A practical example: a format element bound to `Declaration.Item.Amount` tells you which model
path feeds it. Only the model mapping knows that this path is filled from `TaxTrans.AmountCur`,
and only the data model knows the path's type and cardinality. With all three loaded, one click
goes from the output element to the table field.

When you ingest from a live environment, the ancestor data models of the configurations you select
are pulled in automatically, and model mappings are fetched for each of those data models — the
tool tries to complete the picture without you having to hunt for the dependencies.

## The Explorer

The Explorer shows every loaded configuration as a tree: configuration → containers, datasources,
or format elements → their children. By default the configurations are grouped by kind — data
models, model mappings, formats. It has a few controls worth knowing:

- **Filter** — narrows the tree to nodes matching what you type.
- **Kind chips** — one each for data model, model mapping, and format; switch a kind off to hide
  it when you have many files loaded.
- **Sort** (in the ⋮ menu) — **Load order**, **Name ascending (A–Z)**, or **Name descending
  (Z–A)**.
- **Show model hierarchy / Show flat list** (in the ⋮ menu) — the hierarchy view groups each data
  model with the mappings and formats built on it, instead of listing every configuration side by
  side. On a workspace with a dozen files it is usually the view you want.

The same ⋮ menu has **Expand entire tree** and **Collapse entire tree**, and **Close all**, which
closes every configuration — with **Reopen** in the notification if you did not mean it. Each
row's own ⋮ menu offers what fits the node, such as **Where used** or closing the configuration.

## The workspace manager

The **Workspace manager** (the button in the Explorer header) is the full picture of what is
loaded: every configuration grouped by its data model, with its kind and whether it came from a
file or from F&amp;O. From there you can:

- filter the list, add more files with **Add files…**, or jump to the F&amp;O download panel with
  **Add from F&amp;O…**,
- open a configuration in a tab, close individual entries, or **Close all**,
- re-add something you closed earlier from **Available (closed / cached)** — one at a time with
  **Add to workspace**, or everything with **Open all** — and **Remove from cache** what you no
  longer need.

Closed configurations stay in the browser cache and can be reopened any time. When you add a
format or a model mapping back, the manager asks **Also load related configurations?** and offers
the related data model and mapping in the same step — that is normally what you actually wanted,
and it saves a second trip.

## Recent sessions and configurations

The landing page offers back what you worked on before, in two lists.

**Recent sessions** are the sets of configurations that were open together, titled by the format
they were about. Each shows when it was open, how many configurations it held, and where they came
from (**Local files**, or `F&O · <host>` for an environment), and lists its configurations with
their versions — click one to add just that configuration. **Open** restores the whole session;
when a workspace is already open the button reads **Add to open** and adds the session to what is
there. The ⋯ menu has **Close what is open and open this session** and **Remove from history**.
Closing everything keeps the last workspace in the list as a session, so it is one click away.

**Recent configurations** lists configurations one by one: name and version, kind, source (a file
name, or `F&O · <host>`), and when it was opened. Click one to add it to the workspace. With a long
history a filter appears, and **Show all** expands the list. An entry whose content is no longer
stored in the browser is marked *not stored in the browser* and has to be opened again from disk
or downloaded again.

## What happens to your files

Nothing leaves your browser. Files are read with the browser's file APIs and parsed by code running
in your tab; there is no upload step and no server-side copy.

Configuration XML **is** kept locally, though, so the app can offer it back to you: the full content
of every file you load goes into your browser's IndexedDB storage, and the landing page and the
workspace manager use it to re-open a recent configuration — or a whole previous session — without
you picking the files again. The recent lists themselves, your preferences (theme, language, view
mode) and your connection profiles sit in the browser's local storage; nothing about any of it is
sent anywhere.

**Clear history** in **Recent configurations** empties the cache — **Remove from history** on a
single entry drops just that configuration — while **Clear history** in **Recent sessions** only
forgets the sessions. Both show **Undo** in a notification for a few seconds before anything is
deleted. Clearing the site's data in your browser removes all of it.

## Files that will not load

If a file fails to parse, a notification names the file and the reason (*Failed to load …*); a file
that is not `.xml` at all is listed under **Load errors** on the landing page. The usual causes:

- The file is a Finance &amp; Operations **derived configuration** with no XML of its own — there
  is nothing to parse. Load its base configuration instead.
- The XML is truncated, or was saved as a different artifact (a report definition, a package
  manifest) rather than an ER configuration.

See [Troubleshooting](/docs/troubleshooting) if a file you expected to work does not.
